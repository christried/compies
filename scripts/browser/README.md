# Browser checks

Headless Chrome driven over the DevTools protocol, one profile per account, so the Dev Host and the Dev Member are signed in side by side. For the browser check of `docs/agents/subagents.md` § Supervision when Claude in Chrome isn't there, and for every ticket with live behaviour or motion. No dependency: Node 24 and an installed Chrome (`CHROME_PATH` if it isn't in the usual place).

Needs `pnpm dev` and, for anything live, `pnpm dev:realtime` (README § Realtime). Profiles and screenshots go to `<tmp>/compies-browser/`, and a check that logs through `results(name)` writes its lines and screenshots to its own folder there.

A new check imports two modules. Both read `COMPIES_SLOT` (§ Port slots): `chrome.mjs` for the Chrome ports and profile folders, `kit.mjs` for the default base. `chrome.mjs` is the DevTools protocol and knows nothing about COMPIES: `launch(account, { scrollbars })` (ports per account in `PORTS`; the accounts are the four dev Users `host`, `member`, `admin` and `member2`, #599; `scrollbars: true` leaves Chrome its classic scrollbar, 15 px at 1440 px, which the kit hides otherwise, #780), `launchAll(accounts, options)` / `closeAll(tabs)`, `tab.send` / `tab.evaluate`, `resize` (returns once the page has the new width, #780), `colorScheme(tab, value)`, `shot(tab, name, selector, dir)`, `sleep`. `COMPIES_CHROME_FLAGS` adds flags to every Chrome a script launches, split at spaces: a sound check sets `COMPIES_CHROME_FLAGS=--autoplay-policy=no-user-gesture-required` where the page's sound must run without a gesture, and leaves it out where the check is about sound held back (#537). Every Chrome is launched with Blink settings that make it report a hovering fine pointer, whatever the machine has (#780): left to itself it answers `(hover: hover)` as the machine does, and Tailwind puts every `hover:` rule inside that query. The setting applies from each page load on; a phone tab (below 600 px) still reports a coarse pointer without hover; and a `resize()` puts the machine's own answer back until the next page load. A check of the page without hover at desktop width brings its own `--blink-settings=primaryHoverType=1,availableHoverTypes=1,primaryPointerType=2,availablePointerTypes=2` in `COMPIES_CHROME_FLAGS`, which replaces the kit's. `kit.mjs` is what a COMPIES check needs on top:

- `results(name)`: the check's folder `<tmp>/compies-browser/<name>/` with `check(label, passed, measured)`, `skip` and `note` (each line printed and appended to its `results.log` at once, after a header with the script and the tested SHA; a log of another commit in that folder is set aside as `results-<sha>.log` first, #599), `shot` and `failed`. The tested SHA is the kit's own commit, and against an https base the one in `COMPIES_TESTED_SHA`, the commit that base serves, with the kit's beside it (#780);
- `open(tab, path, width, height, waitFor, { news, appearance, setup, tour })`: the dev sign-in, with the Nuxt devtools hidden; `appearance: 'dark' | 'system'` signs the User in on that Appearance (light when absent), `setup: true` signs in a User who has not set up yet, `tour: true` leaves the Rundgang unseen (a plain sign-in marks it seen, so it never covers a page; only the walk's Rundgang states ask, #810; the path is `signInPath(…)`); `openSignedOut(tab, path, width, height, waitFor, { appearance, plain })`: the page as a visitor with that Appearance's cookie sees it (signs in, signs out through the route, loads `path`; returns `'route'` or `'cookies'`); `colorScheme(tab, 'dark')` from `chrome.mjs` sets the device's scheme, which is what System follows; `finePointer(tab, fine)`, called before `open()`, makes `matchMedia('(pointer: fine)')` answer `fine` in the page's JavaScript: Chrome's media emulation ignores `pointer`, and a CSS `@media (pointer: fine)` rule does not follow the helper (#599). Since #780 the kit's Chrome reports a fine pointer by itself, so the helper's use is `finePointer(tab, false)`, the page without one;
- `api(tab, method, path, body)`, and `ok(answer, what)` for its body (it throws unless the answer is a 200);
- the scenario helpers `createGame`, `createEvent`, `joinEvent`, `runningEvent(tabs, { name, games, set, settings })` (one Party per tab, the Session started, games set), `finishedEvent(tabs, { name, outcome: 'winner' | 'tie', games })` (on top of it: every game set, Results for the outcome, the Finish), `setGame`, `enterResult` with `placesOf(order)`, `eventView`, `patchSettings` (throws when the answer lacks the change);
- a User's hands: `clickText`, `mouseClick`, `typeInto`, `pressKey`, `drag(tab, from, to, { touch })`, `stepperNext`; and the page read back: `textOf`, `visibleButtons`, `switches`, `animations(tab)`, `motionOf(tab, selector)` (the element's running animations with the curve each really runs on: a CSS animation keeps it on its keyframes and reports `linear` on the effect) and `shadowOf(tab, selector)` (the layers of its `box-shadow` a User sees, without Tailwind's transparent ones), both #780.

A browser-check agent writes its own scripts in `scratch/` here (gitignored), so they import `../kit.mjs` from whichever worktree runs them (`docs/agents/browser-frame.md`).

The game edit route is `/bibliothek/<id>/bearbeiten`; `?s=edit` is an artboard state, not a route.

## Port slots

Two sessions can serve at once, because the scripts take a slot: `COMPIES_SLOT=1` (the default) is :3000 for the app, :8787 for the Worker, :3001 for the production server and :9311 to :9314 for the Chromes; `COMPIES_SLOT=2` is each plus 100. `serve.mjs` also takes `--slot=2`. The variable has to be set for `serve.mjs` and for each script (`COMPIES_SLOT=2 node scripts/browser/pool-preview.mjs`; in PowerShell `$env:COMPIES_SLOT = '2'`). Slot 2 starts the Worker allowing the slot's app origins and starts the app with the slot's Worker address (`REALTIME_URL`) and `BETTER_AUTH_URL`. Its production server gets the Worker address at runtime too (`NUXT_PUBLIC_REALTIME_URL`), because the build bakes in the one it was built with. `wrangler.jsonc`, `.env` and `.env.example` keep slot 1's values, and the run's flags and variables override them. A script's default base is the slot's app (`BASE_URL` still wins: the production build of slot 2 is `http://localhost:3101`). Slot 2's Chromes use their own profile folders (`profile-<account>-slot2`), because one Chrome profile serves one browser at a time and cookies ignore ports. One run name and one worktree serve one slot. The dev database and the dev Users stay shared, so `dark.mjs` does not run on one slot while another check measures on the other.

## Staging

A check runs against staging with `BASE_URL=https://staging.compies.christried.me` and the staging project's „Protection Bypass for Automation“ secret in `VERCEL_AUTOMATION_BYPASS_SECRET` (Vercel → the project → Settings → Deployment Protection). `open()` then visits `/api/health` once per profile with the bypass query, which sets Vercel's bypass cookie, and signs in through the dev route as on `pnpm dev`; the secret reaches staging only, never a header on every request. So 390 px on staging, which Claude in Chrome cannot show (retro 0.10), is one call:

```
BASE_URL=https://staging.compies.christried.me VERCEL_AUTOMATION_BYPASS_SECRET=… node scripts/browser/shots.mjs e/<slug>
```

The secret is a credential like every other: it lives in `.env` (gitignored; the scripts read it with `node --env-file=.env …`) or in the user's `!` command, never in a transcript, an issue or a report. `.env` is copied into every agent worktree, so a check agent can run against staging (`docs/agents/browser-frame.md` § Staging); the kit uses the secret only when `BASE_URL` is an https address, so a script on localhost that loads `.env` sends it nowhere (#599). Test data lands on the staging database and follows `docs/agents/delivery.md` § Issues, „Events on staging“. The Worker and `pnpm dev` stay off: a staging check talks to the deployed app alone. First run on 2026-11-15 (#599): the Dev Host at 1440 px and `member2` at 390 px, each signed in on staging, 14 of 14 checks.

Limits:
- Headless Chrome never starts the browser's own image drag, so a native drag problem shows only on a real device. `nativeDrags` catches the ones it does start.
- It signs in through `/api/dev/sign-in`, which `pnpm dev` and the staging build carry (#247) and production never does: production needs the user. Staging sits behind Vercel Authentication, which § Staging passes; without the secret, a Player check on staging signs in with `https://staging.compies.christried.me/api/dev/sign-in?as=member&to=/e/<slug>` in Claude in Chrome (`claude --chrome`), at the desktop width only.
- `shots.mjs` without a selector captures the viewport: pass the selector of anything below the fold (e.g. `'section:has(> dl)'` for „So wird gespielt“).
- A `pnpm dev` started in the background outlives its stopped shell on Windows (TaskStop ends the shell, not nuxt, the Worker or workerd), and an agent may not `taskkill` a PID: start and stop the servers with `serve.mjs`.
- `Network.setBlockedURLs` doesn't block WebSockets in headless Chrome. To check a failed connect, point the page at a port nothing listens on: `REALTIME_URL=http://localhost:8788 pnpm dev` (the Worker runs on 8787, and the shell's value wins over `.env`).
- A check of a list or a wheel covers its edges (`CODING_STANDARDS.md` § Tests): `createGame` with a name of `GAME_NAME_MAX` characters, and a pool of one game. The dev library's names are all short („Alpha mvyc0op7“).
