# Subagents

The orchestrating session (Opus) plans, briefs, supervises and decides; subagents implement and review. These rules win over any skill or hand-off note that names another model, such as "always pass `model: "opus"`".

**Why:** the user wants the cheaper model on every task a precise brief can carry, with Opus controlling everything that lands.

## Model per subagent

Pass `model` and `effort: "high"` on every Agent call. `CLAUDE_CODE_SUBAGENT_MODEL=haiku` in `.claude/settings.json` only catches a spawn that leaves the model out.

Rate each task by the hardest thing it asks, the way `/christried-implement-spec-max` § Model tiers does, against the work this repository realistically has. The harder half of that work runs on Sonnet, the easier half on Haiku, both at high effort (the user, 2026-11-10; before, Haiku was the default and Sonnet the exception):

- **`sonnet`**: a task that section rates Fable (a risk a green test run can hide), or a feature with its own edge cases that the brief can't all settle in advance (#274, #333, #335, #337). Also both `code-review` sub-agents (Standards and Spec) and the three Release reviewers, since a review has to reason about correctness.
- **`haiku`**: a task that section rates Sonnet (the brief settles every decision), work built to a reference such as motion to `04-motion.md` and an artboard (#276, #340, #348), a review follow-up that merges or splits components (#362 to #366), and the review report merger.
- A ticket's brief drafter (§ Briefs, `docs/agents/drafter-frame.md`), implementer and merge job run on the ticket's model. Rate the ticket from its text and the spec before the drafter, and again from the brief: a brief that names a risk raises it. A browser check runs on `haiku` for layout on one account, on `sonnet` for motion or the two-account check.
- In doubt between the two, take Sonnet.
- Implementers and reviewers never run on `opus`, with one exception: under `/christried-implement-spec-max` (`.claude/skills/christried-implement-spec-max/SKILL.md`) every subagent, from the brief drafter to the Release reviewers, runs on the tier its task rates in that skill's § Model tiers: `fable`, or `opus` or `sonnet` with `effort: "high"`. The rest of this document applies there unchanged.

Reviewers, the `code-review` sub-agents and the Release review alike, brief drafters and merge jobs run with `isolation: "worktree"`, so none of them touches the main checkout: a reviewer told to stay read-only still checked out a detached head there (0.5.1), and a merge there landed on another session's branch (2026-11-10).

## Briefs

One brief per ticket, written by a brief drafter on the ticket's model. The drafter's frame is `docs/agents/drafter-frame.md`: what a brief holds, the drafter's steps and what it returns. The spawn prompt names the ticket, the integration branch, the file in the orchestrator's scratchpad to write the brief to, the frame as `git show origin/<integration branch>:docs/agents/drafter-frame.md`, and the migration number when the ticket has one, counted over the merged and running tickets of its spec.

The orchestrator reads the brief rather than the code, checks it against the frame's § The brief and the ticket, settles the questions, and edits it before the spawn. It opens the code only where the brief touches a secret or is unsure. In 0.7 the orchestrator wrote every brief from the code itself, and that reading, with the diffs, filled its 300k context in each of the five sessions. A statement the brief makes about another ticket goes onto an issue only once the orchestrator has checked it (the frame's step 4). A brief's changelog line is checked against the banned list in `test/unit/changelog-file.test.ts` before the spawn, so the implementer never meets it in CI. The more precise the brief, the more of the work Haiku can take.

A brief for a ticket whose predecessor is not merged yet is drafted after that merge: drafted before it, the brief for #315 needed nine edits for a two-case change once the predecessor landed.

Around the brief goes the frame, `docs/agents/implementer-frame.md`: worktree base, commits, changelog line, checks and report. A new worktree starts from `main`, where a frame changed on `staging` isn't yet, so the spawn prompt names it as `git show origin/<integration branch>:docs/agents/implementer-frame.md`. A merge job gets `docs/agents/merger.md`. Run at most three implementers at a time and one merge job at a time; more overloads the machine (session 6 of 1.4).

## Supervision

Review every implementer's work against its brief and the ticket's acceptance criteria before it merges, and against the integration tip: a merge resolution can bring back code another ticket just removed. Read the diffstat first, then the files the brief marks risky; open the full diff only for a seam the brief doesn't name (0.9: full diffs of 66 KB and 15k-token reports put every session at the context limit). Merge it only once CI is green on the head it reported (`node scripts/ci-wait.mjs <sha> --until-done` with `run_in_background` says so, or why not, re-runs a zero-job run, a GitHub start failure, once by itself, and follows a run that a newer push to its branch cancelled to that branch's newer head, saying „superseded by <sha>“ (a run cancelled by hand stays red); without the flag a call ends after 2.5 minutes with exit 2, which the background reports as a failed task, three times in session 5 of 0.10), then add its changelog line on the integration branch (`docs/agents/release.md` § Changelog lines).

The orchestrator merges a clean branch itself, once CI is green on the head and the head contains the integration tip, with `node scripts/merge-into.mjs <integration branch> <head> --base <the integration tip you reviewed against> -m "Merge <branch> (#<n>)" -m "<the attribution lines>"` (`--base` is optional; give it). The script builds the merge commit from the trees and pushes it, and touches no working tree, so another session switching the main checkout cannot redirect the merge (2026-11-10: a merge in the main checkout landed on `feat/427-tag-colours`). Exit 0 prints the merge commit: name it on the issue and wait for CI on it. Exit 1 lists the conflicting paths and writes nothing: that is a merge job's (`docs/agents/merger.md`). Exit 2 refuses and writes nothing: the integration branch moved since you reviewed it (review the new tip, then merge again), the head is already in it, or the push was rejected. The attribution lines go in as their own `-m` paragraph, so the merge commit carries them like any commit (session 4 of 0.10 forgot them once). It costs a few hundred tokens where a merge job costs ≈ 55k and 2–3 minutes (0.9, sessions 4 and 5). Answer a report only with a fix list, and accept it by merging, without a reply: a finished agent stays idle, and a message wakes it to send its report again (all three times in session 7 of 0.8).

A ticket that changes a page isn't done on tests alone: look at the page on `pnpm dev` at 390 and 1440 px wide, signed in through `/api/dev/sign-in?as=host` or `?as=member` (README), with the edge cases its brief names, and compare it with its `.dc.html` artboard in `docs/design_handoff_compies/reference/`. The PR's Evidence lists what the check showed (page, account, width, what was compared); the screenshots stay in `<tmp>/compies-browser/`, and the key ones go to the user with SendUserFile (`gh` cannot upload images). A ticket with live behaviour (two people on one Event) or motion also gets the two-account check in `scripts/browser/`: a Host and a Member in two headless Chrome profiles, with every animation logged. A browser check run by a subagent (its model as § Model per subagent says, `isolation: "worktree"`) gets a brief of the items to check and the frame `docs/agents/browser-frame.md` (setup, measuring rules, report), named in the spawn prompt like the implementer frame. Tickets that share a page or a component are checked together, in one brief on the latest integration tip, because browser checks serialise on ports :3000, :8787 and :3001 of slot 1 (session 2 of the 0.10 follow-ups ran four single-ticket checks where one would have done). An implementer measuring a fix, or the layout items its brief marks „measure on slot 2“, takes slot 2 (`docs/agents/browser-frame.md` § Port slots, `docs/agents/implementer-frame.md` § Checks); the orchestrator posts an item the implementer measured with its measured literal. Once no implementer runs, a second check agent takes slot 2 beside the one on slot 1, each from its own prepared check worktree: 0.13.2's ten runs, one after another on slot 1, took four hours and 2.1 M subagent tokens. A check on staging (390 px there, or a verification that would fill the orchestrator's context) goes to a check agent on the frame's staging path (`docs/agents/browser-frame.md` § Staging), once `.env` holds the bypass secret. A brief holds up to six items, and one above six splits by theme (motion apart from layout), so the first report comes earlier: 0.10's ten-ticket check took 55 minutes and 415k tokens in one agent.

**Context limit.** Before every new implementer (`implement-spec` steps 4, 6 and 7), run `node scripts/context-usage.mjs <session id>` with your own session id: the folder above your scratchpad directory (`<tmp>/claude/<hash>/<session id>/scratchpad`), also in `$CLAUDE_CODE_SESSION_ID`. It reads that session's context from its transcript in the main checkout's project folder, so it gives the same answer from a worktree and measures you, not another session writing at the same time; subagents don't count. Without an id it takes the session in $CLAUDE_CODE_SESSION_ID when that session has a transcript; only when the variable is unset or has no transcript does it take the newest transcript, and it exits 2 then when another transcript of the project changed in the last ten minutes: pass the id (a cloud session may lack the variable). At 300k tokens or more, start no new implementer: let the running ones report, review and merge them as usual, then write a handoff for the next session and stop. `handoff` is user-invoked, so read `.claude/skills/handoff/SKILL.md` and follow it. The handoff carries what a fresh `/implement-spec` needs to go on without loss:
- the spec, the integration branch, its PR, and each ticket's state: merged, in flight (branch, worktree), on the frontier, or blocked (by what);
- every subagent still running, by its ticket and the description it was spawned with: only the session that spawned an agent can resume it (SendMessage), so one a usage limit stops is resumed from this session, not the next (retro 0.8, finding 6);
- the brief of every ticket not yet merged, copied next to the handoff (briefs live in this session's scratchpad);
- every decision the user made in chat, first posted as a comment on its issue, then pointed to;
- the notes for the Release PR: a link to the comment „For the Release PR“ on the spec issue, which holds them (`docs/agents/delivery.md` § Issues), not a copy of them;
- the friction worth a `/retro`: what cost time, what a check, a doc or a brief should have caught.

**`/handoff` while subagents run.** When the operator calls `/handoff` while subagents still run, the orchestrator pulls them back first, without being asked (0.11: the operator had to ask twice, and both handoffs were rewritten). It messages each running subagent (SendMessage): stop; commit and push what you have to your branch (a work-in-progress commit is fine, CI may be red); reply with the branch, the head commit, what is done and what is left. It waits for every reply. A subagent still silent after ten minutes is recorded as silent, with its worktree path. Then it writes the handoff once, with one row per subagent (ticket, branch, head, what is done, what is left), in place of the subagent bullet above, so the next session can start a fresh implementer on each pushed branch. The operator's `/handoff` arguments override this: „let them finish“ means waiting for their reports instead. The automatic path at 300k stays as it is: let running agents report, review and merge them, then hand off.

End by telling the user the handoff's path, to start the next session with `/implement-spec` and that path. A `/retro` followed by an `/implement-spec` in one session starts the run near the limit (session 1 of the 0.10 follow-ups began at 239k), so run `/clear` between them.

The orchestrator does every merge into `staging` and `main` (`docs/agents/delivery.md`).
