# COMPIES audit, 2026-10-24

Whole repo at `staging` 0f6db8f. Read like the developer who inherits it and gets paged when it breaks.

**What this repo does:** COMPIES is a Nuxt 4 web app (installable as a PWA, a web app you can put on your home screen) where a group of friends picks dates for game nights. A Host creates an Event, shares an Invite link, Members vote on proposed times (Slots), the Host sets each Session's Date, and everyone downloads a calendar file (.ics). The server is Nitro API routes on Vercel (region `fra1`), the database is Postgres on Neon through Drizzle, and sign-in is Discord or Twitch through Better Auth.

**Load assumed:** one group of friends. Tens of Users, a handful of open Events, a few browser tabs that each ask the server for news every 15 s. Nothing below depends on more load than that.

**What I ran:** `pnpm test` (48 files, 564 tests, all pass), `pnpm lint` and `pnpm typecheck` (both clean). Findings 1 and 4 were confirmed with throwaway tests outside the repo (results quoted below). No repo code was changed.

---

## Must fix

### 1. Everyone is signed out 7 days after signing in, however often they use the app (#64)
(`server/utils/user.ts:21-26`, `app/middleware/auth.global.ts:18-25`)

- **What this is:** Every API call checks the login through `getUser`, which asks Better Auth for the login session. When a session is more than a day old, Better Auth pushes its end date 7 days out and sends a new login cookie, so active Users stay signed in. `auth.global.ts` is written to pass that new cookie on to the browser.
- **Problem:** `getUser` calls `auth.api.getSession({ headers })` as a plain function. In that form Better Auth returns only the session data and throws the new cookie away. So the database extends the session, but the browser cookie keeps the 7-day lifetime it got at sign-in. The loop in `auth.global.ts` never finds a cookie to pass on. A throwaway test confirmed it: a two-day-old session was extended in the database (`expires_at` moved from 29.10. to 31.10.), `/api/me` sent no `Set-Cookie`, and the same call with `returnHeaders: true` returns `better-auth.session_token=…; Max-Age=604800`.
- **Fix:** Ask for the headers and pass the cookie on, in `getUser`:
  ```ts
  const { headers, response: authSession } = await useAuth(event).api.getSession({ headers: event.headers, returnHeaders: true })
  for (const cookie of headers.getSetCookie()) appendResponseHeader(event, 'set-cookie', cookie)
  if (!authSession) return null
  ```
  Then the existing loop in `auth.global.ts` starts working for page loads too. Test (in `test/integration/profile.test.ts`): sign in, set `auth_sessions.expires_at` to now + 5 days, `GET /api/me`, expect a `session_token` cookie in the answer.
- **If we skip it:** Each User signs in again every week. For a weekly game-night app, that is almost every visit. Together with finding 3, an open tab then shows a generic error instead of the sign-in page.

### 2. Removing a Session can erase the "delete this from your calendar" warning (#65)
(`server/api/e/[slug]/sessions/[id].delete.ts:29`, `app/pages/e/[slug].vue:172-178`)

- **What this is:** When the Host withdraws a Session's Date (Reopen, „Neue Terminsuche“), the old Date is kept in `previous_starts_at`, and every Member sees „Der Termin … wurde aufgehoben, bitte aus deinem Kalender löschen“. That notice exists so nobody shows up on the wrong evening (spec #1, story 61).
- **Problem:** Removing a Session deletes its row, and the warning goes with it. Two cases:
  - The Host removes a Session that has a Date („Entfernen“ on its card). Members who downloaded the .ics keep that evening in their calendars, and the app never tells them.
  - Event with two dated Sessions. The Host reopens Session 2, so Members get the notice. Then the Host decides one evening is enough and taps „−“ next to „1 Termin gesucht“. The „−“ removes the last Session without a Date, which is the one carrying the notice. Members who have not opened the app in between never see it.
- **Fix:** Don't delete a Session that has, or had, a Date. Add a `removed_at` column instead. On removal, set `removed_at = now()`, `previous_starts_at = coalesce(starts_at, previous_starts_at)`, `starts_at = null`, `slot_id = null`. `eventSessions` skips removed rows, so counts, numbers, Phase and the .ics stay as they are. The Event read also returns removed rows that have a `previous_starts_at`, only for the notices. A Session that never had a Date is still really deleted. Test (in `test/integration/manage-sessions.test.ts`): remove a dated Session, and a Member's Event read still shows its notice. This is also a product call: if the Host is expected to tell the group in chat, write that down instead.
- **If we skip it:** Friends turn up, or keep the evening free, for a Session that no longer exists.

## Should fix

### 3. A lost login in an open tab shows "something went wrong" instead of the sign-in page (#66)
(`app/pages/index.vue:50-62`, `app/pages/e/[slug].vue:29`, `app/pages/e/[slug].vue:89-94`)

- **What this is:** The route guard decides "signed in or not" once per page load. After that, the pages keep calling the API: every 15 s, on focus, and on each vote.
- **Problem:** When the login cookie runs out (weekly today, see finding 1; after 7 idle days once 1 is fixed) or the User signs out in another tab, every call answers 401 (meaning "not signed in"). No code handles 401. Home shows the generic error with „Erneut versuchen“, which fails again. The Event page shows the generic state, and votes show „hat nicht geklappt“. Only a full reload reaches the sign-in page, and an installed PWA has no reload button.
- **Fix:** One client plugin that sends any 401 to sign-in, reusing the guard's own redirect:
  ```ts
  // app/plugins/signed-out.client.ts
  export default defineNuxtPlugin(() => {
    globalThis.$fetch = $fetch.create({
      onResponseError({ response }) {
        if (response.status !== 401) return
        useAuthUser().value = null
        const redirect = guardRoute(useRoute(), null)
        if (redirect) navigateTo(redirect)
      },
    })
  })
  ```
  Test (nuxt project): `/api/e` answers 401, and the page ends on `/anmelden?redirect=…`.
- **If we skip it:** Users get stuck on an error screen with no hint that they only need to sign in again.

### 4. The calendar title changes without a new SEQUENCE when an Event goes from one Session to two (#67)
(`server/domain/session.ts:59-68`, `server/domain/ics.ts:137-139`)

- **What this is:** Each calendar entry has a stable id (UID) and a version number (SEQUENCE). A calendar app only replaces an entry it already has when the version goes up. `sequenceRaises` decides which versions go up. Spec #55: "so a re-import updates the titles".
- **Problem:** The title names the Session number only while the Event has more than one Session (`sessions.length === 1` in `sessionEntries`). `sequenceRaises` only looks at times and numbers. Adding a second Session changes the first one's title from „Spieleabend (Compies)“ to „Spieleabend · Session 1 (Compies)“, but its number stays 1, so nothing is raised. Confirmed: before `Spieleabend (Compies) | SEQUENCE 0`, after `Spieleabend · Session 1 (Compies) | raised: []`. Removing back down to one Session has the same gap.
- **Fix:** In `sequenceRaises`, also raise every remaining Session when the count crosses one:
  ```ts
  // The title names the Session's number only while the Event has several Sessions (ics.ts sessionEntries).
  const titleFormChanged = (before.length > 1) !== (after.length > 1)
  ```
  and let `titleFormChanged` pass the filter. Test in `test/unit/session.test.ts`: one dated Session plus a new one, and the dated one is in the result.
- **If we skip it:** A re-import keeps the old title, so the calendar entry and the app disagree on what the evening is called. Cosmetic, but it is exactly what #55 promised to avoid.

### 5. A stale 9 MB copy of the design files sits in `docs/`, still using the old word "Session" (#68)
(`docs/Compies whole design process/`, 313 files, 9 MB)

- **What this is:** A snapshot from the first commit (8c08bee) that has never been updated. Nothing in the repo links to it.
- **Problem:** Its `.dc.html` reference files are byte-for-byte copies of `docs/design_handoff_compies/reference/`. Its `design_handoff_compies/*.md` is an old version of the handoff. It still says "Session" for what ADR 0011 renamed to "Event": `03-screens.md` has 30 "Session" and 2 "Event", while the current copy has 7 and 26. Agents and people who grep `docs/` find both copies and can't tell which one is current.
- **Fix:** `git rm -r "docs/Compies whole design process"`. Git history keeps it. If the design history should stay at hand, keep it outside the repo.
- **If we skip it:** Sooner or later an agent builds from the superseded spec. Every clone also carries 9 MB nobody reads.

## Nice to have

### 6. Reschedule takes a detour through two helpers that only it uses
(`server/utils/new-date.ts:11-18`, `server/utils/sessions.ts:48-64`, `server/api/e/[slug]/sessions/[id]/reschedule.post.ts:25-31`)

- **What this is:** The five Session handlers (confirm, add, remove, reopen, reschedule) follow one pattern: read the body, lock the Event, read the Sessions, ask the rule, write, then `finishSessionChange`. Four of them write in place.
- **Problem:** Reschedule alone goes through `readNewDate` and `moveSessionDate`, and each has only that one caller. `readNewDate` also reads the request body inside the transaction, so the Event row lock (which makes Votes wait) is held while the body arrives. Its comment says it serves "a Set Date or Reschedule request", but Set Date doesn't use it. `moveSessionDate`'s `isNotNull` guard repeats a check the locked transaction already made.
- **Fix:** Read the body before the transaction like the other four. Then call `parseLocalTime` and `rescheduleRejection`, `update(sessions).set(rescheduleValues(startsAt))`, `finishSessionChange`, all in the handler. Delete `server/utils/new-date.ts` and `moveSessionDate`. About -25 lines, and the existing reschedule tests cover it.
- **If we skip it:** One more file to read to understand one handler, and a comment that misleads.

### 7. "Open Slots and their Votes" is worked out twice
(`server/api/e/[slug].get.ts:31-38`, `server/api/e/index.get.ts:66-69`)

- **What this is:** Since #52, a Slot that became a Session's Date leaves the poll, along with its Votes. The Event read and Home both apply that rule before `pollStanding`.
- **Problem:** Each handler filters Slots with `openSlots`, builds a set of ids and filters Votes by hand. These are near-copies that have to change together (as they did in #52).
- **Fix:** One pure helper next to `openSlots` in `server/domain/session.ts`, e.g. `openPoll(slots, sessionSlotIds, votes)` returning `{ slots, votes }`, and both handlers call it.
- **If we skip it:** The next poll rule change can land in one place and miss the other.

### 8. "An emoji counts as one" is coded four times, and isn't true for many emoji
(`shared/event.ts:13-15`, `server/domain/profile.ts:7`, `app/pages/einrichten.vue:15`, `app/components/TextField.vue:24`)

- **What this is:** Event names (1–60) and Display names (1–32) are measured "trimmed, an emoji counts as one".
- **Problem:** Four places count with `[...text].length`, which counts code points (the pieces an emoji is built from). 🎲 counts 1, but 👍🏽 and 🇩🇪 count 2, and 👨‍👩‍👧 counts 5. A name full of such emoji is refused early, and the counter under the field shows more than you see.
- **Fix:** One `characterCount(text)` in `shared/` built on the standard `Intl.Segmenter` (`[...new Intl.Segmenter().segment(text)].length`), used in all four places. The profile page's truncation slices by the same segments.
- **If we skip it:** A rare refusal of a valid-looking name, and four copies of one rule.

I left out 4 smaller ones: `Europe/Berlin` is hard-coded in three files; the vote rate limiter has an interface with one implementation across two files; a Reschedule onto the time of an open Slot leaves that Slot votable but impossible to confirm; the mute toggle controls no sound yet (a deliberate choice per its comment).
